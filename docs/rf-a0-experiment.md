# RF-A0 — Native Linux Process

## Primary question

What is a SisTer-class application process from the Linux kernel's point of
view before project-created isolation exists?

RF-A0 uses a newly authored executable as an experimental object. It is not a
reduced `sisterd`, and RF-A0 does not infer verified SisTer requirements from
probe design choices.

## Initial architecture

`srf-runtime-probe` is one small C++23 process using Linux/POSIX primitives. It:

1. opens and retains one regular-file descriptor;
2. creates one TCP listening socket bound explicitly to `127.0.0.1`;
3. reports PID, PPID, real UID/GID, working directory, one controlled
   environment value, resource paths, descriptor numbers, and selected port;
4. waits for connections or a termination request;
5. blocks SIGINT/SIGTERM and receives them through Linux `signalfd` in the same
   poll set as the listener, then performs controlled shutdown.

It contains no generic runtime, deployment, container, namespace, or resource
governance abstraction.

## Prediction-first experiments

The project-local `.hoa/protocols/rf-a0-pre-observation.json` contains prior
understanding, hypotheses, predictions, contradictions, and alternatives but no
observations. The orchestrator hashes it into a run commitment before decisive
collection. `.hoa/learning/rf-a0.json` is the separate post-observation
synthesis.

## Host observation

While the child is alive, the gate captures:

- `/proc/<pid>/status`;
- `/proc/<pid>/fd` links;
- `/proc/<pid>/maps`;
- `/proc/<pid>/mountinfo`;
- `/proc/<pid>/ns` links;
- `/proc/<pid>/cgroup`;
- the relevant `/proc/<pid>/net/tcp` listener row;
- `/proc/<pid>/exe` and the probe's structured standard output.

The gate correlates rather than merely records PID, PPID, executable, regular
descriptor, socket inode/address/port, launcher/probe namespace membership,
cgroup membership, and SIGTERM outcome.

## Evidence policy

Specifications, predictions, and source code are authored inputs. Files under
`docs/experiments/evidence/rf-a0/` are generated by the gate from execution and
carry a checksum for the verification summary. Build-tree outputs remain
transient and are not the sole evidence for any claim.

Textual procfs snapshots preserve fields and lines but remove trailing spaces
and tabs used only for kernel column padding, so governed evidence remains clean
under version-control whitespace checks.

Generated run directories contain platform/toolchain identity, raw procfs
snapshots, signal stress results, machine-readable gate checks, and a chained
run record. Generated analysis separates `OBSERVED`, `INFERRED`, `LEARNED`, and
`NOT_YET_KNOWN`. A passing gate supports only the exact checks it performs in
the recorded environment. Claims that cannot be mechanically proved—especially
independent authorship at fragment level—are identified as audit limitations.

## Scope boundary

RF-A0 observes the baseline supplied by its launcher. Matching namespace IDs do
not show that namespaces are absent; they show only that the probe did not enter
a different namespace relative to the gate for the compared types. Matching
cgroup records do not prove resource governance. A loopback bind does not prove
network isolation. An observed mount table does not prove filesystem isolation.

RF-A0 does not establish container behavior, namespace creation semantics,
resource limits, network isolation, privilege boundaries, persistence design,
operational readiness, or SisTer deployment requirements.

Fedora Linux is the reference execution platform. Kernel interfaces remain the
research subject, but a result from one Fedora userspace, kernel, libc, and
toolchain is not generalized to all Linux environments without further evidence.
